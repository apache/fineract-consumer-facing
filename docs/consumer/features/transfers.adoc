[[transfers]]
= Transfers

The transfers module moves money out of a customer's own savings account and serves the customer's transfer history. It supports three destination cases through a single initiate/confirm endpoint pair: another savings account the customer owns, a saved beneficiary's savings account, and one of the customer's own loan accounts. A loan repayment is not a separate feature: it is a transfer whose destination type is `loan`, executed upstream through the same Fineract account-transfers API, and it is restricted to loans the caller owns; the demo UI surfaces it from the loan detail page rather than the transfers page. The BFF (backend-for-frontend, the Spring Boot service that sits between the Angular client and Fineract Core) validates, authorizes, and challenges the request; Fineract Core performs the actual accounting.

Code lives in `org.apache.fineract.consumer.transfers`, following the repository's CQRS layout (Command Query Responsibility Segregation, the project convention of splitting write-side and read-side code into separate trees): the command side handles the initiate and confirm flow, and the query side serves transfer history.

== Endpoints

All endpoints live under `/api/v1/transfers` and are registered as `authenticated()` in `SecurityConfig` (`/api/v1/transfers/**`), so they require a valid consumer access token (a JWT, a signed JSON Web Token issued by the BFF's own auth stack). Every request must also pass the device-fingerprint filter that applies to all authenticated routes, so the `X-Device-Fingerprint` header is required on the history endpoint as well as the command endpoints.

[cols="1,3,4,4"]
|===
|Method |Path |Purpose |Auth requirements

|POST
|`/api/v1/transfers/initiate`
|Validate the intended transfer, send a one-time password (OTP) to the customer's email, and return a step-up token bound to the exact transfer parameters.
|Consumer JWT with `TRANSFER_EXECUTE` policy satisfied; `X-Device-Fingerprint` header required.

|POST
|`/api/v1/transfers/confirm`
|Verify the step-up token and OTP, re-run all authorization checks, and execute the transfer against Fineract.
|Consumer JWT with `TRANSFER_EXECUTE` policy satisfied; `X-Device-Fingerprint` and `Idempotency-Key` headers required.

|GET
|`/api/v1/transfers`
|List the caller's savings-to-savings transfer history, optionally filtered by date range and paginated.
|Consumer JWT with `TRANSFER_LIST` policy satisfied, plus `SAVINGS_VIEW` authorized for each of the caller's savings accounts during assembly.
|===

Request bodies (`InitiateTransferCommandRequest`, `ConfirmTransferCommandRequest`) share the core fields `fromAccountId`, `toAccountId`, `toAccountType`, and `amount`. `toAccountType` accepts `savings` or `loan` (case-insensitive); any other value fails with HTTP 400 (`TransferInvalidException`). The confirm body adds `stepUpToken` and `otp`. The initiate response (`TransferChallengeCommandData`) returns the step-up token, its expiry, and the masked email the OTP was sent to. The confirm response (`TransferCommandData`) returns the Fineract transfer id plus the echoed accounts and amount. It is the same id the history rows carry (see <<transfers-ids>>).

The history endpoint takes optional `fromDate` and `toDate` query parameters (ISO dates, both inclusive) plus `page` (default 0) and `size` (default 20). Its response (`TransferQueryResponse`) carries the page content along with exact `totalElements` and `totalPages`. Each row (`TransferQueryData`) holds the Fineract transfer id, date, amount, currency code, the source and destination account numbers, and a `direction` of `OUTGOING` or `INCOMING`.

== Transfer flow

`initiate` runs these steps in `TransfersCommandServiceImpl`:

. Resolve the destination type (`savings` or `loan`).
. Authorize `ConsumerAction.TRANSFER_EXECUTE` against the source account through `AccessPolicyEvaluator`.
. Check the destination is allowed (own loan, registered savings beneficiary, or owned savings account; see below).
. Create an email OTP through the `infrastructure.otp` module.
. Issue a step-up token with a 5 minute TTL (`StepUpConstants.STEPUP_TTL`), bound to the user, the device fingerprint, and an action fingerprint: a SHA-256 hash of `endpoint|fromAccountId|toAccountId|accountTypeCode|amount` computed by `StepUpTokenService`. The amount is normalized with `stripTrailingZeros()` before hashing so `10.0` and `10.00` fingerprint identically.

`confirm` recomputes the action fingerprint from the submitted body and verifies the step-up token against it. Changing any parameter between initiate and confirm (source, destination, type, or amount) produces a different fingerprint and the token is rejected with HTTP 401 (`TransferStepUpInvalidException`). It then validates the OTP, re-runs the same authorization and destination checks as initiate, resolves office and client ids from Fineract, and posts the transfer upstream. For a loan destination the destination client and office are the caller's own, since only the caller's loans are permitted; for a savings destination the owning client and office are resolved from Fineract.

== Transfer history flow

The history endpoint covers savings-to-savings transfers only; savings-to-loan transfers are excluded because repayments belong to the loan account view served by the loans module. `TransfersQueryServiceImpl.listTransfers` runs these steps:

. Authorize `ConsumerAction.TRANSFER_LIST` (no resource id; the policy requires the `consumer:full` scope and a true `kyc_verified` claim).
. Resolve the caller's Fineract client id through `UserClientResolver` and list the client's savings accounts (`ClientApi.retrieveAllClientAccounts`).
. For each savings account, authorize `SAVINGS_VIEW`; a denial fails the whole request with HTTP 403 (`TransferQueryAccessDeniedException`). Then fetch the account with its transactions (`SavingsAccountApi.retrieveSavingsAccount` with the `transactions` association) and collect every transaction that carries a transfer reference, keyed by transfer id so the two legs of a transfer between two owned accounts merge into one row. A withdrawal leg sets the source account number; any other leg sets the destination.
. For transfers whose destination leg was not found among the caller's savings accounts, fetch the transfer detail (`AccountTransfersApi.retrieveOne6`, `GET /v1/accounttransfers/{transferId}`). If the upstream destination account type id is 1 (loan), the row is dropped; otherwise the counterparty savings account number is taken from the detail and zero-padded to 9 digits to match Fineract's display format.
. Filter by the optional date range, sort newest first (transfer date descending, then transfer id descending), and page in the BFF over the materialised set, which is why the response carries an exact total.

A row's direction is `OUTGOING` when a withdrawal leg on one of the caller's accounts was found, otherwise `INCOMING`. Any upstream failure is translated to HTTP 502 (`TransferQueryUpstreamUnavailableException`). The cost grows with the caller's account count (N+1 Fineract calls) plus one extra call per transfer whose counterparty leg is outside the caller's savings accounts; nothing is cached or persisted.

== Security controls

Mechanisms are documented centrally; see xref:abac[Attribute-Based Access Control (ABAC)] and xref:step-up[Step-Up Authentication] for the authorization mechanisms and xref:idempotency[Idempotency] for the idempotency design. This section states which controls apply to which endpoint.

[cols="2,2,5"]
|===
|Control |Applies to |As implemented

|Authentication
|All endpoints
|`/api/v1/transfers/**` requires an authenticated JWT (`SecurityConfig`). Cucumber asserts the unauthenticated denial path for both the confirm flow and the history endpoint.

|ABAC ownership
|`/initiate`, `/confirm`
|`AccessPolicyEvaluator.authorize(jwt, TRANSFER_EXECUTE, fromAccountId, ...)`. The `TRANSFER_EXECUTE` policy in `ActionPolicies` requires the `consumer:full` scope (open banking tokens are denied), a true `kyc_verified` claim, and ownership of the source savings account resolved through `OwnedAccountsCache`. Denials publish an `ACCESS_DENIED` audit event and return HTTP 403.

|ABAC history
|`GET /api/v1/transfers`
|`TRANSFER_LIST` is an unowned policy requiring the `consumer:full` scope and a true `kyc_verified` claim, then `SAVINGS_VIEW` is authorized per savings account during assembly; a per-account denial returns HTTP 403 (`TransferQueryAccessDeniedException`).

|Destination policy
|`/initiate`, `/confirm`
|`requireDestinationAllowed`: a `loan` destination must be an active loan the caller owns with a positive outstanding balance, and the amount cannot exceed the current payoff amount returned by `prepayLoan` (failing with HTTP 422 `TransferLoanOverpaymentException` or `TransferLoanNotActiveException`). A `savings` destination is first matched against the caller's active savings beneficiaries; if the matched beneficiary has a `transferLimit`, an amount above it fails with HTTP 403 (`TransferBeneficiaryLimitExceededException`). With no beneficiary match, the caller must own the destination savings account.

|Step-up authentication
|`/confirm`
|Step-up token verified against subject, device fingerprint, and action fingerprint (`StepUpTokenService.verify`); OTP validated by the `infrastructure.otp` module. OTPs are stored as SHA-256 hashes, expire after 300 seconds, are deleted on first successful validation, and are deleted after 5 failed attempts. The step-up token itself is not single-use, but confirm always consumes an OTP, so a full confirm cannot be replayed.

|Idempotency
|`/confirm`
|`Idempotency-Key` header is mandatory, validated by `IdempotencyKeyPolicyEvaluator` (1 to 64 visible ASCII characters, else HTTP 400). `IdempotencyKeyDeriver` hashes `userPublicId:rawKey` with SHA-256 so keys are namespaced per user, and a Feign interceptor (`FineractIdempotencyKeyInterceptor`) forwards the derived key to Fineract as its own `Idempotency-Key` header. Deduplication is performed by Fineract; a retry with the same key returns the original transfer id. An upstream HTTP 425 (request still processing) is translated to `TransferInProgressException` (HTTP 425).

|Rate limiting
|All endpoints
|No transfer-specific limit. The infrastructure-level per-user `RateLimitFilter` applies as it does to all authenticated endpoints, and OTP validation is capped at 5 attempts per challenge.

|Secret hygiene
|`/initiate`, `/confirm`
|`ConfirmTransferCommand` and `TransferChallengeCommandData` use `@ToString(onlyExplicitlyIncluded = true)` so the OTP and step-up token never appear in logs. The initiate response masks the OTP destination email (`EmailMaskingService`).
|===

== Interaction with the beneficiaries module

The dependency is one-way: transfers depends on the beneficiaries query side, never the reverse. `TransfersCommandServiceImpl` calls `BeneficiariesQueryService.findActiveByAccount(userId, toAccountId)` and reads `BeneficiaryQueryData.getTransferLimit()`. The lookup matches active savings-type beneficiary rows only; loan destinations never consult beneficiaries. The beneficiary lookup runs before the ownership check, so a registered destination's `transferLimit` applies even if the caller happens to own the account, although in practice the beneficiaries module refuses to register the caller's own accounts. Only the `beneficiaries.query.service` and `beneficiaries.query.data` packages are consumed, which matches the project convention that a module exposes only its `service` and `data` packages; `ModulithArchitectureTest` verifies module boundaries with Spring Modulith. The `transfer_limit` column is defined in the beneficiaries changelog (`db/changelog/beneficiaries/003-create-beneficiaries.yaml`) and owned by that module; transfers only enforces it.

== Fineract integration

Both sides use generated Feign clients (declarative HTTP clients generated from Fineract's OpenAPI specification) from `infrastructure.fineractclient.generated`:

* `ClientApi.retrieveOneClient` resolves the caller's (and, for savings destinations, the destination owner's) office id, which the account-transfers API requires.
* `ClientApi.retrieveAllClientAccounts` (`GET /v1/clients/{clientId}/accounts`) lists the caller's savings accounts for history assembly.
* `SavingsAccountApi.retrieveSavingsAccount` resolves the owning client of a savings destination on the command side, and fetches each account with its transactions on the query side.
* `AccountTransfersApi.createAccountTransfer` executes the transfer: `POST /v1/accounttransfers` on Fineract Core.
* `AccountTransfersApi.retrieveAllAccountTransfers` (`GET /v1/accounttransfers?accountDetailId=...`) resolves the transfer id the confirm response returns.
* `AccountTransfersApi.retrieveOne6` (`GET /v1/accounttransfers/{transferId}`) resolves the counterparty leg of a history row and identifies loan destinations to exclude.

[[transfers-ids]]
Fineract keeps a transfer in two tables: its details (accounts, offices, type) in `m_account_transfer_details`, and the transfer itself, with its savings transactions, in `m_account_transfer_transaction`. `POST /v1/accounttransfers` answers with the details id. Savings transactions and `GET /v1/accounttransfers/{transferId}` use the transfer's id, so the history does too. The two ids match only while every set of details has exactly one transfer: each standing instruction adds details with no transfer, so in practice they differ. Confirm therefore looks up the transfer under the returned details (`TransferFineractClient.getAccountTransferId`) and returns that id. If the lookup fails after the transfer went through, confirm answers HTTP 502; a retry with the same `Idempotency-Key` gets Fineract's cached answer to the create, so it moves no money and returns the transfer id.

Loan repayments do not use Fineract's loan transaction API. They are posted through the same `POST /v1/accounttransfers` call with `toAccountType` code `1` (loan); savings destinations use code `2`. The source is always a savings account (`fromAccountType` is hard-coded to `2`). On the query side loan destinations are identified by the upstream account type id (1) rather than a display string.

Command-side upstream failures are translated by `FineractCaller`: 404 becomes `TransferNotFoundException`, 400 becomes `TransferInvalidException`, 425 becomes `TransferInProgressException`, and anything else becomes `TransferUpstreamUnavailableException` (HTTP 502). Query-side upstream failures all become `TransferQueryUpstreamUnavailableException` (HTTP 502).

== Money handling

Amounts are `BigDecimal` from the request body through to the upstream call; no floating-point types appear anywhere in the module. Bean Validation enforces `@NotNull @Positive` on the amount and both account ids. The amount is serialized to Fineract with `toPlainString()` (no scientific notation) alongside a fixed `en` locale and `yyyy-MM-dd` date format. The transfer date is the BFF server's current date (`LocalDate.now()`), and the description is the constant `"Consumer initiated transfer"`. The BFF does not carry or validate a currency field; currency compatibility between the two accounts is enforced by Fineract Core.

== Data model

The module owns no BFF tables. There is no `transfers` directory under `db/changelog`, no JPA entity, and no repository. All durable transfer state lives in Fineract Core, and transfer history is assembled from Fineract on every request rather than read from a BFF store. The only BFF-side state touched during a transfer is transient and owned by other modules: the pending OTP hash (`infrastructure.otp`) and the derived idempotency key held for the duration of the upstream call (`IdempotencyKeyHolder`, set before the write and cleared in a `finally` block).

== Design rationale

The two-phase initiate/confirm design keeps the BFF stateless about pending transfers. Instead of persisting a draft transfer row, the step-up token carries a hash of the exact transfer parameters, so the confirm request proves both possession of the challenge and that the parameters did not change. This avoids a table, a cleanup job, and a class of stale-draft bugs.

All authorization checks run twice, once per phase. Confirm cannot trust that initiate ran its checks because account ownership, beneficiary status, or KYC state can change between the two calls, and because confirm is an independent HTTP request that must stand on its own.

Idempotency is delegated to Fineract rather than deduplicated in a BFF table because Fineract is the system of record for the money movement; a BFF-side dedupe could disagree with upstream reality after a partial failure. Deriving the forwarded key from the user id prevents one user's key from colliding with, or probing, another's.

The query side owns transfer history because it is a cross-account view: per-account transaction lists already belong to the savings and loans modules, but a single list of the customer's transfers spans accounts and needs transfer-specific leg merging. It reads Fineract directly instead of persisting a BFF-side transfer log because Fineract is the system of record; a BFF copy could diverge after partial failures. Savings-to-loan transfers are excluded from the history because repayments are presented on the loan account view; including them here would duplicate the loan module's transaction history.

== Limitations and future work

* *Transfers execute immediately.* They use the server's current date; there is no scheduling, no future-dated transfer, and no recurring transfer.
* *The transfer description is a fixed constant.* The customer cannot attach a note.
* *No amount ceiling on own-savings transfers.* Transfers between the customer's own savings accounts are bounded only by the optional per-beneficiary `transferLimit` (loan repayments are capped at the loan's current payoff amount returned by `prepayLoan`). A global or per-tier transaction limit would need new policy data.
* *The OTP channel is hard-coded to email.* This applies to the transfer step-up flow.
* *Loan payoff validation is best-effort and non-locking.* The initiate and confirm lookups check the current payoff amount returned by Fineract's `prepayLoan` template, but do not acquire an exclusive lock in Fineract. Concurrent confirmations can both pass the validation, and retries may observe a loan that was already closed.
* *Confirm-time validation can make idempotent retries on full loan payoff fail with HTTP 422.* Because `requireDestinationAllowed()` validates that the loan is active before setting the idempotency key, retrying a confirm request after a network failure on a full payoff will fail with HTTP 422 (`TransferLoanNotActiveException`) because the loan is now closed in Fineract, rather than reaching Fineract's idempotency replay mechanism.
