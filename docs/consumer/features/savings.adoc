= Savings

The savings module provides consumer views of a customer's savings accounts and supports savings account applications. The query side serves savings reads: the account list, account detail with balances, account charges, transaction history, and the application template. The command side serves savings application writes: submit, modify, and withdraw. It follows the project CQRS convention (CQRS: commands and queries are separated end to end).

Code lives under `consumer/src/main/java/org/apache/fineract/consumer/savings/`, with `query/` for reads and `command/` for writes.

== Endpoints

All endpoints are served under the base path `/api/v1/savings` and return JSON. Every request must carry a valid access JWT (JSON Web Token, the signed token minted at login), which the security filter chain reads from the `access_token` httpOnly cookie. There are no public savings endpoints.

Each endpoint additionally passes through the ABAC policy check (ABAC: attribute-based access control, authorization decided from attributes of the caller, the resource, and the request) for the listed action. All savings actions require the `kyc_verified` JWT claim to be `true`.

=== Query endpoints

Served by `SavingsQueryController` under `/api/v1/savings`.

[cols="1,3,4,4", options="header"]
|===
| Method | Path | Purpose | Authorization

| GET
| `/api/v1/savings`
| List the caller's savings accounts (id, account number, product name, status code, active flag, currency code).
| Action `SAVINGS_LIST`. Scope `consumer:full` or `openbanking:accounts.read`. KYC required.

| GET
| `/api/v1/savings/{savingsId}`
| Account detail: account number, product name, status code, active flag, balance, available balance, nominal annual interest rate, currency code.
| Action `SAVINGS_VIEW` with ownership check on `savingsId`. Scope `consumer:full` or `openbanking:accounts.read`. KYC required.

| GET
| `/api/v1/savings/{savingsId}/charges`
| Charges attached to the account (id, name, amount, amount outstanding, currency code).
| Action `SAVINGS_VIEW` with ownership check. Same scopes as above.

| GET
| `/api/v1/savings/{savingsId}/transactions`
| Paginated transaction search returning a page envelope. Query parameters: `fromDate` and `toDate` (optional, ISO dates, `yyyy-MM-dd`), `page` (default `0`), `size` (default `20`), `sort` (optional, `field` or `field,direction`).
| Action `SAVINGS_VIEW` with ownership check. Same scopes as above.

| GET
| `/api/v1/savings/{savingsId}/transactions/{transactionId}`
| Single transaction detail (id, type, amount, currency code, running balance, date).
| Action `SAVINGS_VIEW` with ownership check on `savingsId`. Same scopes as above.

| GET
| `/api/v1/savings/template`
| Savings application template. Without `productId`: the list of savings products (id, name) for browsing. With `productId`: that product's detail (currency, interest rate, compounding, posting, and calculation settings).
| Action `SAVINGS_APPLICATION_TEMPLATE_VIEW`. Scope `consumer:full` only. KYC required. No ownership check (products are not owned resources).
|===

=== Command endpoints

Served by `SavingsCommandController` under `/api/v1/savings`. Every command additionally requires an `Idempotency-Key` header (a client-supplied unique value that makes a retried request safe); a missing header is rejected by Spring, a malformed one by `IdempotencyKeyPolicyEvaluator`. None of these commands requires a step-up token.

[cols="1,3,4,4",options="header"]
|===
|Method |Path |Purpose |Authorization

|POST |`/api/v1/savings` |Submit a new savings account application. The submission date is set server-side (today in the tenant timezone) and the interest rate is taken from the product; consumers cannot choose either. Returns 201 with `{savingsId, resourceId, clientId}`. |`SAVINGS_APPLICATION_SUBMIT`; scope `consumer:full`; `Idempotency-Key` required.

|PUT |`/api/v1/savings/{savingsId}` |Modify a pending savings account application (change product). The submission date is reset server-side. Only SAVINGS-type accounts (deposit type 100) may be modified; fixed and recurring deposit accounts are rejected. |`SAVINGS_APPLICATION_MODIFY`; scope `consumer:full`; caller must own the savings account; `Idempotency-Key` required.

|POST |`/api/v1/savings/{savingsId}?command=withdrawnByApplicant` |Withdraw a pending savings account application. The withdrawal date is set server-side and the note is limited to 1000 characters. Any other `command` value is rejected with 400. |`SAVINGS_APPLICATION_WITHDRAW`; scope `consumer:full`; caller must own the savings account; `Idempotency-Key` required.
|===

The `openbanking:accounts.read` scope appears on the list and view actions because the open banking module (`consumer.openbanking`) reuses `SavingsQueryService` to serve consent-scoped third-party reads. Consumer sessions carry `consumer:full`.

== Ownership and ABAC checks

Every service method calls `AccessPolicyEvaluator.authorize(...)` (in `consumer.infrastructure.access`) before any Fineract call. The evaluator checks, in order: a policy exists for the action, the JWT scope claim intersects the policy's allowed scopes, the `kyc_verified` claim is true, and, for owned actions, the caller owns the resource. Any failure publishes an `ACCESS_DENIED` audit event and throws; ownership denials on savings throw `SavingsQueryAccessDeniedException` (HTTP 403, code `error.msg.consumer.savings.query.access.denied`).

Ownership works as follows. `UserClientResolver` maps the JWT subject (the BFF user's public UUID) to the bound Fineract client id via a database lookup. `OwnedAccountsCache` then resolves the set of savings and loan account ids that client owns by calling Fineract `GET /v1/clients/{clientId}/accounts`, cached in a two-level cache (in-process Caffeine, 60 second TTL, backed by Valkey, 300 second TTL). The requested `savingsId` must be in that set. A `savingsId` the caller does not own is rejected at the BFF; the request never reaches Fineract.

The list endpoint has no per-resource check because it is scoped by construction: the service resolves the caller's own client id and asks Fineract only for that client's accounts.

See xref:abac[Attribute-Based Access Control (ABAC)] for the general policy model, the policy table, and the caching and eviction rules.

== Fineract integration

`SavingsQueryServiceImpl` calls Fineract through the generated Feign client (Feign: a declarative HTTP client; the interfaces are generated from Fineract's OpenAPI specification into `consumer.infrastructure.fineractclient.generated`). No hand-written Feign interfaces are used in this module. Upstream endpoints, verified against the generated client:

[cols="3,4", options="header"]
|===
| BFF operation | Fineract endpoint

| List accounts
| `GET /v1/clients/{clientId}/accounts` (`ClientApi.retrieveAllClientAccounts`)

| Account detail
| `GET /v1/savingsaccounts/{accountId}` (`SavingsAccountApi.retrieveSavingsAccount`)

| Charges
| `GET /v1/savingsaccounts/{savingsAccountId}/charges` (`SavingsChargesApi.retrieveAllSavingsAccountCharges`)

| Transaction search
| `GET /v1/savingsaccounts/{savingsId}/transactions/search` (`SavingsAccountTransactionsApi.searchTransactions`)

| Single transaction
| `GET /v1/savingsaccounts/{savingsId}/transactions/{transactionId}` (`SavingsAccountTransactionsApi.retrieveOneSavingsAccountTransaction`)

| Product list and product detail (template)
| `GET /v1/savingsproducts` and `GET /v1/savingsproducts/{productId}` (`SavingsProductApi`)
|===

Command endpoints call Fineract through the same generated Feign client:

[cols="3,4", options="header"]
|===
| BFF operation | Fineract endpoint

| Submit application
| `POST /v1/savingsaccounts` (`SavingsAccountApi.submitSavingsApplication`)

| Modify application
| `PUT /v1/savingsaccounts/{accountId}` (`SavingsAccountApi.updateSavingsAccount`)

| Withdraw application
| `POST /v1/savingsaccounts/{accountId}?command=withdrawnByApplicant` (`SavingsAccountApi.handleCommandsSavingsAccount`)

| Deposit-type pre-check
| `GET /v1/savingsaccounts/{accountId}` (`SavingsAccountApi.retrieveSavingsAccount`)
|===

Upstream errors are translated by the shared `FineractCaller` wrapper: an upstream 404 becomes `SavingsAccountNotFoundException` (404) or, on the product path, `SavingsProductNotFoundException` (404); an upstream 400 becomes `SavingsRequestInvalidException` (400) or, on the product path, `SavingsUpstreamUnavailableException` (502); any other Feign failure becomes `SavingsUpstreamUnavailableException` (502). Fineract response bodies never reach the client on error paths; the standard exception handler serializes only the BFF error code and default message.

One workaround exists: Fineract's OpenAPI spec declares the single-transaction response as a plain string, so the generated client returns raw JSON text for that call. The service deserializes it manually into `SavingsAccountTransactionData` with the Jackson `ObjectMapper`.

== DTO mapping policy

Fineract response shapes never pass through to the Angular client. Each operation maps the generated Fineract model into a module-owned read model in `savings/query/data/`: `SavingsAccountListItemQueryData`, `SavingsAccountQueryData`, `SavingsChargeQueryData`, `SavingsTransactionQueryData`, `SavingsApplicationTemplateQueryData`, and `SavingsProductOptionQueryData`, plus the page envelope `SavingsTransactionQueryResponse`. Mapping is a deliberate subset: only the fields the consumer UI needs are carried over.

Command requests map from module-owned request DTOs in `savings/command/data/` (`SubmitSavingsApplicationCommandRequest`, `ModifySavingsApplicationCommandRequest`, `WithdrawSavingsApplicationCommandRequest`) into generated Fineract request models inside the service layer. Command responses map from generated Fineract response models into `SavingsApplicationCommandData` (`savingsId`, `resourceId`, `clientId`).

Fineract's enum-option objects (`{id, code, value}` triples for status and transaction type) are flattened to their stable `code` string (for example `savingsAccountStatusType.active`); the localized display `value` is not exposed. Account read models additionally carry a boolean `active` flag derived from the status object. The application template detail exposes each enum setting as an id and code pair (for example `interestCompoundingPeriodTypeId` and `interestCompoundingPeriodTypeCode`). Currency objects are reduced to the currency code. Monetary and rate fields (`balance`, `availableBalance`, `amount`, `runningBalance`, `amountOutstanding`, `nominalAnnualInterestRate`) are `java.math.BigDecimal` end to end; no floating-point types touch money. Dates are `java.time.LocalDate`.

== BFF state

The module stores nothing. There is no `repository/` or `domain/` package, no JPA entity, and no Liquibase changeset for savings. Every read is a live pass-through to Fineract. The only state involved is the ownership cache described above, which is infrastructure owned by the access package, not by this module.

A submit evicts the caller's entry in `OwnedAccountsCache` so the newly created savings account passes ownership checks immediately instead of after the cache TTL.

* Unit tests: `SavingsQueryServiceImplTest` covers the list mapping, the empty-list case, translation of an upstream failure to `SavingsUpstreamUnavailableException`, the ownership denial on account detail, currency mapping on account detail, charges, and single transaction, the split of `sort` into Fineract's `orderBy` and `sortOrder` (including a bare field name), and the empty page envelope when Fineract returns no content.
* Unit tests: `SavingsCommandServiceImplTest` covers submit/modify/withdraw authorization, deposit-type pre-check rejection for non-SAVINGS accounts, derived idempotency key lifecycle, idempotency replay translation, upstream error translation, cache eviction on submit, access-denied means no upstream call, `ArgumentCaptor` field mapping for all three commands, and product allow-list enforcement.
* Unit tests: `SavingsCommandControllerTest` covers request validation constraints (`@NotNull`, `@Positive`, `@Size`), idempotency key enforcement into commands, and malformed-key rejection.
* End-to-end tests: `savings.feature` (Cucumber, run against the full Docker stack) covers listing seeded accounts, fetching account detail, currency presence on account, charge, and transaction amounts, rejection without a session (401), denial when reading another client's account (403), double submit with one idempotency key, submit without an idempotency key, modify a pending application, withdraw a pending application, cross-client modify/withdraw denial, withdrawing an active account, and withdrawing an already-withdrawn application.
* The summary feature's Cucumber scenarios exercise the savings read path indirectly through the account-summary aggregation.
* A Playwright spec (`frontend/playwright/tests/savings.spec.ts`) covers the frontend route guard: an unauthenticated visit to the savings page redirects to login.

== Design rationale

* Stateless passthrough with a command side. Fineract is the system of record for savings; persisting application state in the BFF would create a dual-write problem. The BFF's value is authorization, DTO translation, idempotency plumbing, and server-side date derivation (consumers cannot pick submission or withdrawal dates).
* Deposit-type guard. Modify and withdraw pre-check that the target account's `depositType` is `SAVINGS` (100) before calling Fineract, preventing fixed/recurring deposit accounts from being re-pointed or withdrawn through the savings path.
* Product allow-list. `consumer.savings.command.allowed-product-ids` (comma-separated product IDs) restricts submit and modify to consumer-offered products. When unset, all products are accepted; configure it in production to limit self-service to intended products.
* Ownership enforced in the BFF. Fineract's own authorization is back-office shaped and is not trusted as the consumer policy enforcement point. Failing early also avoids leaking existence information about other clients' accounts.
* The service is exposed as an interface (`SavingsQueryService`) so the open banking module can reuse the exact same read path under a narrower token scope instead of forking a second savings client. The ABAC action table, not the module, decides which scopes may invoke each operation.
* Thin DTOs keep the Angular client decoupled from Fineract's large response shapes and prevent accidental exposure of upstream fields that were never reviewed for consumer visibility.

== Limitations and future work

* *Only date and sort filters are exposed.* Fineract's transaction search supports filtering by amount range, transaction type, and submitted date; the BFF exposes only `fromDate`, `toDate`, and `sort`. Additional filters would be additive parameters on the existing endpoint.
* *No statement document generation (PDF or export).* "Statements" means the filterable transaction list.
* *Ownership checks read a cached account set.* The cache uses 60 s / 300 s TTLs, so an account added to a client mid-session may be denied until the cache entry expires or is evicted.
* *No consumer UI.* The command API is implemented but there is no Angular frontend to submit, modify, or withdraw savings applications. A customer-facing apply/withdraw flow (with a Playwright journey) is tracked separately; see issue #144 for the broader self-service feature set.
* *Product allow-list not pre-populated.* `consumer.savings.command.allowed-product-ids` defaults to accepting all products. Operators should configure it to restrict self-service to intended savings products before enabling in production.
