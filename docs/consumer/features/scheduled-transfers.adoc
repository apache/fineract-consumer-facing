[[scheduled-transfers]]
= Scheduled Transfers

The scheduled transfers module lets a customer set up a recurring transfer out of one of their own savings accounts: weekly or monthly, from a start date, with an optional end date. The destination is another savings account the customer owns or a registered savings beneficiary. The BFF validates, authorizes, and challenges the request, then creates a Fineract *standing instruction*; Fineract Core runs every transfer itself, in its *Execute Standing Instruction* job. The BFF has no scheduler of its own.

Code lives in `org.apache.fineract.consumer.scheduledtransfers`. Customers can set up a scheduled transfer, list their active ones, see each one's run history, and cancel one. While a transfer to a beneficiary is active, the beneficiary cannot be deleted or have its limit lowered below the transfer's amount (see <<scheduled-transfers-beneficiary-guard>>).

== Feature flag

The module is behind `consumer.scheduled-transfers.enabled`, which is `false` by default. While it is off, every scheduled-transfer endpoint answers HTTP 404 with code `error.msg.consumer.scheduledtransfers.disabled` before any other check runs (`ScheduledTransferDisabledException` on the command side, `ScheduledTransferQueryDisabledException` on the query side; both carry the same code). The local compose stack turns it on through `CONSUMER_SCHEDULED_TRANSFERS_ENABLED`.

The flag is read per call by `ScheduledTransfersCommandServiceImpl` and `ScheduledTransfersQueryServiceImpl`, not through `@ConditionalOnProperty`: AOT processing evaluates bean conditions at build time, so a native image would ignore a runtime setting (see xref:native-image[Native Image]).

=== Runbook: turning the feature off

Turning the flag off stops customers from creating scheduled transfers through the BFF. It does *not* stop the transfers they already set up:

* Every instruction already created stays active in Fineract, and the *Execute Standing Instruction* job keeps running it until its end date, or forever if it has none.
* The BFF keeps its `scheduled_transfers` rows. Turning the flag back on restores the feature with nothing lost.
* To stop an instruction, staff delete it in the Fineract back office (or call `PUT /v1/standinginstructions/{id}?command=delete`). Each instruction the BFF created is named `Consumer recurring transfer <publicId>`, where `<publicId>` is the `public_id` of its `scheduled_transfers` row; `fineract_standing_instruction_id` on that row holds the instruction id.
* Customers have no way to see or cancel these instructions while the flag is off. Tell them before turning it off, and agree whether staff will cancel their instructions or let them run.
* The beneficiary guard still applies while the flag is off (see <<scheduled-transfers-beneficiary-guard>>). A customer whose instruction pays a beneficiary cannot delete that beneficiary, or lower its limit below the instruction's amount, until staff delete the instruction.

Fineract only runs instructions while its *Execute Standing Instruction* job (`STI_EXEC`) is active. It is active by default and runs daily at midnight; deactivating it pauses every standing instruction in the tenant, not only those created through the BFF.

== Endpoints

All endpoints live under `/api/v1/scheduled-transfers`, registered as `authenticated()` in `SecurityConfig` (`/api/v1/scheduled-transfers/**`), and require a consumer access token. The writes also require the `X-Device-Fingerprint` header.

Both request bodies carry `fromAccountId`, `toAccountId`, `amount`, `frequency` (`WEEKLY` or `MONTHLY`), `startDate`, and an optional `endDate` (ISO dates). The confirm body adds `stepUpToken` and `otp`. The initiate response (`ScheduledTransferChallengeCommandData`) returns the step-up token, its expiry, and the masked email the OTP was sent to. The confirm response (`ScheduledTransferCommandData`) returns only the scheduled transfer's `publicId`.

The cancel initiate takes no body and returns the same `ScheduledTransferChallengeCommandData`. The cancel confirm body carries only `stepUpToken` and `otp`.

The list returns `ScheduledTransferQueryData` items: `publicId`, `fromAccountId`, `toAccountId`, `amount`, `frequency`, `startDate`, and `endDate` (inclusive, absent when there is none). The run history returns a `ScheduledTransferRunQueryResponse` page (`content`, `page`, `size`, `totalElements`, `totalPages`) of `ScheduledTransferRunQueryData` items: `date`, `status` (`SUCCEEDED` or `FAILED`), and `amount`, which is absent on a failed run because nothing moved. `totalElements` and `totalPages` count the runs in the requested window, not the transfer's whole history.

== Schedule rules

* *Frequency.* `WEEKLY` or `MONTHLY`, every period. A weekly transfer runs on the start date's weekday. A monthly transfer runs on the start date's day of the month; in a month without that day (the 31st in April, say) it runs on the month's last day. Fineract does this since FINERACT-2914, which the pinned image includes; older Fineract versions skip such a month instead.
* *Start date.* Must be after Fineract's current date, so the first run is never on the day the customer sets it up. That date is the business date when business dates are enabled, otherwise today in the tenant's time zone, and the BFF reads it from Fineract (see <<fineract-today>>) rather than using its own clock. Fineract's job runs once a day on that date and never catches up a date it has passed, so a start date the BFF thought was tomorrow but Fineract had already reached would silently lose its first run.
* *End date.* Optional and inclusive: the last day a run may happen. It must not be before the start date. Fineract's `validTill` is exclusive, so the BFF sends the day after.
* *Destination.* Must differ from the source. A registered savings beneficiary is accepted if the amount is within its `transferLimit`; otherwise the customer must own the destination savings account.
* *Currency.* Both accounts must hold the same currency. Fineract does not check this when it accepts an instruction (every run would fail instead), so the BFF does.
* *Amount.* Positive, a fixed amount per run. Partial transfers are never allowed: a run with insufficient funds fails instead of moving part of the amount.

A start or end date that breaks these rules, or a destination equal to the source, fails with HTTP 400 (`ScheduledTransferInvalidException`). An amount above the beneficiary limit fails with HTTP 403 (`ScheduledTransferBeneficiaryLimitExceededException`), a destination that is neither owned nor a beneficiary with HTTP 403 (`ScheduledTransferAccessDeniedException`), and a currency mismatch with HTTP 422 (`ScheduledTransferCurrencyMismatchException`).

[[fineract-today]]
=== Fineract's current date

`BusinessDateFineractClient.today()` reads `transferDate` from `GET /v1/accounttransfers/template`, called with no parameters. Fineract fills it from the same date its jobs use, whether or not business dates are enabled. `GET /v1/businessdate/BUSINESS_DATE` is not used: it returns the stored row only, so it is 404 on a tenant that never set a business date and stale once business dates are disabled again. The value is cached in memory for 30 seconds. If Fineract cannot be reached or reports no date, `initiate` and `confirm` fail with HTTP 502 (`ScheduledTransferUpstreamUnavailableException`).

== Creation flow

`initiate` runs these steps in `ScheduledTransfersCommandServiceImpl`:

. Check the feature flag.
. Authorize `ConsumerAction.SCHEDULED_TRANSFER_CREATE` against the source account.
. Check the schedule rules, reading Fineract's current date for the start date, and the destination.
. Read both accounts from Fineract and compare currencies.
. Send an OTP for `OtpPurpose.SCHEDULED_TRANSFER`.
. Issue a step-up token bound to the action `scheduled-transfers:create` and every parameter: source, destination, frequency, amount, start date, and end date.

`confirm` checks the flag, verifies the step-up token against the submitted parameters, validates the OTP, and re-runs the authorization and schedule checks. It then:

. *Reserves a row.* It inserts a `scheduled_transfers` row keyed by the derived idempotency key, before anything is sent to Fineract, and claims it for this confirm (`claimed_until`, five minutes ahead). If a row with that key already exists and is linked to an instruction, confirm returns its `publicId` without calling Fineract. If it exists unlinked, confirm claims it in one conditional update; when another confirm with the same key still holds the claim, it fails with HTTP 425 (`ScheduledTransferInProgressException`) and the caller retries. Without the claim, that other confirm could delete the row after a failed re-check while this one created the instruction, leaving an instruction with no row.
. *Re-checks the destination and currency.* This happens after the reservation, and the beneficiary is read under a share lock, so a beneficiary deleted or given a lower limit meanwhile is either caught here or sees the reserved row (see <<scheduled-transfers-beneficiary-guard>>).
. *Creates the instruction* through `StandingInstructionFineractClient`, forwarding the derived idempotency key.
. *Links the row* to the returned instruction id and publishes a `SCHEDULED_TRANSFER_CREATED` audit event, in one transaction.

If Fineract rejects the request, or the destination is no longer allowed, the reservation is deleted and the error is returned. If the outcome is unknown (HTTP 425 or 502), the reservation is kept and its claim given up: Fineract may have created the instruction, and a retry with the same `Idempotency-Key` sends the same derived key, so Fineract replays the original id and the row is linked.

[[scheduled-transfers-cancel]]
== Cancellation flow

A customer cancels a scheduled transfer by its `publicId`, with the same initiate/confirm step-up as setting one up. Cancelling deletes the standing instruction in Fineract (`PUT /v1/standinginstructions/{id}?command=delete`), so the job stops running it. The BFF keeps the `scheduled_transfers` row, so the cancelled transfer's run history stays readable.

`initiateCancel` runs these steps in `ScheduledTransfersCommandServiceImpl`:

. Check the feature flag.
. Look the row up by `publicId` and the caller. Another customer's transfer answers HTTP 404 (`ScheduledTransferNotFoundException`), the same as one that does not exist.
. Authorize `ConsumerAction.SCHEDULED_TRANSFER_CANCEL` against the row's source account (HTTP 403, `ScheduledTransferAccessDeniedException`).
. Find the instruction in Fineract, as described below.
. Send an OTP for `OtpPurpose.SCHEDULED_TRANSFER`, and issue a step-up token bound to the action `scheduled-transfers:cancel` and the transfer's `publicId`.

`confirmCancel` checks the flag, verifies the step-up token, validates the OTP, and re-runs the lookup, the authorization, and the instruction check. It then deletes the instruction, forwarding the derived idempotency key, and publishes a `SCHEDULED_TRANSFER_CANCELLED` audit event.

*Finding the instruction.* A linked row names its instruction by id, read with `GET /v1/standinginstructions/{id}`. An unlinked row is matched by the name its `publicId` determines among the client's instructions, as the list does (see <<scheduled-transfers-reads>>). Either way the instruction must debit the row's source account; if Fineract has no such instruction, cancelling answers HTTP 404. An unlinked row a confirm is still working on (its claim has not lapsed) answers HTTP 425 (`ScheduledTransferInProgressException`), and the caller retries.

*Linking before deleting.* Fineract renames an instruction when it deletes it (it appends `_deleted_<id>`), so a row matched by name would lose its instruction, and with it its run history. Confirm therefore links an unlinked row to the instruction it found before deleting it. The link is one conditional update that succeeds only while no confirm holds a claim on the row; if a confirm claimed it meanwhile, cancelling answers HTTP 425.

*Idempotency.* Cancelling a transfer that is already cancelled succeeds. Fineract does not reject a second delete of the same instruction and would rename it again, so confirm reads the instruction's status first and does not call Fineract when it is already deleted (status `3`), whether by an earlier cancel whose response was lost or by bank staff. The derived idempotency key is forwarded on the delete, so a delete Fineract is still processing for the same key answers HTTP 425 instead of running twice. The audit event is published by every successful confirm, including one that finds the transfer already cancelled: each records a cancellation the customer confirmed with an OTP.

If Fineract cannot be reached or fails, confirm answers HTTP 502 (`ScheduledTransferUpstreamUnavailableException`) and publishes no audit event. Whether the delete happened is then unknown; cancelling again settles it either way.

[[scheduled-transfers-reads]]
== Listing and run history

Both reads live in `ScheduledTransfersQueryServiceImpl`. They start from the customer's `scheduled_transfers` rows, so only transfers set up through the BFF are ever shown: a standing instruction bank staff created on the same account, such as a loan repayment, is not. A row is matched to its Fineract instruction by `fineract_standing_instruction_id`. A row is left unlinked when confirm's outcome was unknown and nobody retried; such a row is matched by the instruction name its `publicId` determines, so an instruction Fineract did create is still shown. Either way the instruction's source account must be the row's. The query side never writes the link; only a retried confirm or a cancel does (see <<scheduled-transfers-cancel>>).

The list:

. Checks the flag and authorizes `ConsumerAction.SCHEDULED_TRANSFER_LIST`.
. Reads the customer's rows, newest first. With none, it returns an empty list without calling Fineract.
. Checks that the caller still owns each distinct source account (`AccessPolicyEvaluator.ownsResource`) and leaves out the transfers from any it no longer owns, so one such account does not fail the whole list. With none left, it returns an empty list without calling Fineract.
. Reads the client's standing instructions from Fineract in one paged call (`listClientStandingInstructions`) and keeps each row whose instruction is active: Fineract status `1` (active), and a `validTill` after Fineract's current date (<<fineract-today>>), not the BFF server's. Fineract leaves an instruction active after its end date, so the date is checked too. The end date returned is `validTill` minus one day.

The run history:

. Checks the flag, the page parameters, and the date window, and authorizes `SCHEDULED_TRANSFER_LIST`. A negative `page`, a `size` outside 1 to 100, or a `fromDate` after `toDate` answers HTTP 400 (`ScheduledTransferQueryInvalidException`).
. Looks the row up by `publicId` and the caller. Another customer's transfer answers HTTP 404 (`ScheduledTransferQueryNotFoundException`), the same as one that does not exist.
. Authorizes `SAVINGS_VIEW` on the source account.
. Settles the window. A `fromDate` that is given is used as it is. Without one, the window starts twelve months before Fineract's current date (<<fineract-today>>), not the BFF server's; if Fineract cannot be reached or reports no date, the read answers HTTP 502 (`ScheduledTransferQueryUpstreamUnavailableException`). A `toDate` that falls before that default start is also rejected with HTTP 400. Without a `toDate`, the window is open at the end.
. Reads the source account's run history for that window only from Fineract (`listSavingsAccountRunHistory`, which sends `fromDate` and `toDate` with a `dateFormat` and `locale`). Fineract cannot filter it by instruction, so the BFF keeps the runs of this transfer's instruction, newest first, and pages them. The cost of a request therefore depends on the window and the number of runs in it on the source account, not on the account's age.

Each run is mapped to its date, its outcome, and, for a successful run, the amount moved. The date is Fineract's `executionTime`: the day the job ran, by the tenant's clock rather than its business date. The two are the same day unless a deployment runs Fineract on a business date that differs from the calendar. Fineract records `success`, `failed`, or `partial`; a partial run only happens when `allowPartialTransfer` is true, which the BFF never sets, so any other status is left out. Fineract's `errorLog` is never passed on.

== Security controls

Mechanisms are documented centrally; see xref:abac[Attribute-Based Access Control (ABAC)], xref:step-up[Step-Up Authentication], and xref:idempotency[Idempotency].

[cols="2,2,5"]
|===
|Control |Applies to |As implemented

|Authentication
|All endpoints
|`/api/v1/scheduled-transfers/**` requires an authenticated JWT. Cucumber asserts the unauthenticated denial for the create, list, and cancel endpoints.

|ABAC ownership
|`/initiate`, `/confirm`, `/{publicId}/cancel/initiate`, `/{publicId}/cancel/confirm`
|`AccessPolicyEvaluator.authorize(jwt, SCHEDULED_TRANSFER_CREATE, fromAccountId, ...)`, or `SCHEDULED_TRANSFER_CANCEL` against the row's source account when cancelling. The policy requires the `consumer:full` scope (open banking tokens are denied), a true `kyc_verified` claim, and ownership of the source savings account. A denial returns HTTP 403 (`ScheduledTransferAccessDeniedException`) and publishes an `ACCESS_DENIED` audit event.

|ABAC on reads
|`GET` endpoints
|`AccessPolicyEvaluator.authorize(jwt, SCHEDULED_TRANSFER_LIST)`, an unowned policy requiring the `consumer:full` scope and a true `kyc_verified` claim, then, for the run history, `SAVINGS_VIEW` on the source account (HTTP 403, `ScheduledTransferQueryAccessDeniedException`). The list checks ownership of each source account instead and leaves out the transfers from any the caller no longer owns. The run history also requires the scheduled transfer to be the caller's (HTTP 404 otherwise).

|Destination policy
|`/initiate`, `/confirm`
|A registered savings beneficiary's `transferLimit` is enforced (HTTP 403 above it). With no beneficiary match, the customer must own the destination (HTTP 403 otherwise). Checked at initiate, and again at confirm after the reservation, with a share lock on the beneficiary.

|Step-up authentication
|`/confirm`, `/{publicId}/cancel/confirm`
|Step-up token verified against subject, device fingerprint, and action fingerprint (`scheduled-transfers:create` with every parameter, or `scheduled-transfers:cancel` with the transfer's `publicId`); OTP validated for `OtpPurpose.SCHEDULED_TRANSFER`. Either failing returns HTTP 401 (`ScheduledTransferStepUpInvalidException`).

|Idempotency
|`/confirm`, `/{publicId}/cancel/confirm`
|`Idempotency-Key` header mandatory and validated by `IdempotencyKeyPolicyEvaluator`. The derived key is unique in `scheduled_transfers`, so a retry returns the same `publicId` and Fineract is asked to create the instruction at most once per key. A cancel forwards its derived key on the delete and never deletes an instruction that is already deleted.

|Secret hygiene
|All writes
|Request bodies and `ScheduledTransferChallengeCommandData` use `@ToString(onlyExplicitlyIncluded = true)`, so the OTP and step-up token never reach a log. The initiate response masks the email address.
|===

[[scheduled-transfers-beneficiary-guard]]
== Beneficiary guard

Fineract keeps running a standing instruction whatever happens to the beneficiary it pays. So while a scheduled transfer to a beneficiary is active, the beneficiaries module refuses to delete the beneficiary or to lower its `transferLimit` below the transfer's amount, each with HTTP 409 and its own code:

* `DELETE /api/v1/beneficiaries/{publicId}` answers `error.msg.consumer.beneficiaries.command.scheduled.transfer.active` (`BeneficiaryScheduledTransferActiveException`).
* `PUT /api/v1/beneficiaries/{publicId}/initiate` and `/confirm` answer `error.msg.consumer.beneficiaries.command.limit.below.scheduled.transfer` (`BeneficiaryLimitBelowScheduledTransferException`) when the new limit is below an active transfer's amount. A limit that stays the same, rises, or is removed is not checked; a limit set where there was none is.

The response carries only the code. The customer sees which transfers block the change in the scheduled transfers list, whose rows carry `toAccountId`; cancelling them lifts the guard.

*No module cycle.* `scheduledtransfers` depends on `beneficiaries` for its destination checks, so the check goes through a port: `beneficiaries.command.service.BeneficiaryScheduledTransferLookupPort`, implemented by `scheduledtransfers.query.service.BeneficiaryScheduledTransferLookupAdapter`.

*What counts.* The adapter reads the customer's `scheduled_transfers` rows to the beneficiary's account (index `idx_scheduled_transfers_user_to_account`). With none, it calls Fineract for nothing. A row that is unlinked and still claimed by a confirm counts, whatever its amount, since that confirm may be creating its instruction right now. For the others it reads the client's instructions and finds each row's instruction as the list does: by id when linked, by name otherwise, debiting the row's source account. An instruction counts while it is active and not past its end date by Fineract's date; if Fineract reports no date, an instruction with an end date counts. The amount compared against a new limit is the instruction's, read from Fineract, since staff can edit it. Instructions the bank set up never count: the customer can neither see nor cancel them.

*Flag.* The guard ignores `consumer.scheduled-transfers.enabled`, because instructions created while the feature was on keep running after it is turned off (see the runbook above). A deployment that never turned the feature on has no rows, so the guard costs one indexed query and never calls Fineract.

*Fails closed.* If Fineract cannot be reached, the delete or update answers HTTP 502 (`BeneficiaryUpstreamUnavailableException`) and changes nothing.

*Racing a confirm.* A confirm reserves its row, then re-reads the beneficiary with a share lock (`BeneficiariesQueryService.findActiveByAccountForShare`, `SELECT ... FOR SHARE`). A delete, or the confirm of a limit change, locks the beneficiary row for update (`BeneficiaryCommandRepository.findLockedByPublicIdAndUserIdAndActiveTrue`) before it runs the guard, and holds the lock until it commits. (The initiate of a limit change runs the guard without a lock, only to fail before sending an OTP.) Whichever takes its lock second waits for the other:

* If the delete or limit change locks first, the confirm's re-read waits until it commits, then sees the beneficiary gone or the new limit, and the confirm fails and releases its row.
* If the confirm's re-read comes first, its row is already committed, so the guard that follows sees it, claimed, and refuses.

Without the locks, under PostgreSQL's default `READ COMMITTED` isolation, a confirm could read the beneficiary before a delete committed while the delete's guard ran before the reservation committed, and both would succeed.

== Data model

The `scheduled_transfers` table (changeset `scheduledtransfers/010-create-scheduled-transfers.yaml`, entity `scheduledtransfers.command.domain.ScheduledTransfer`) records which instructions the BFF created and for whom:

* `id` (internal) and `public_id` (the UUID returned to the customer and used in the instruction name).
* `user_id`, a foreign key to `users`.
* `idempotency_key`, the derived key, unique.
* `fineract_from_account_id` and `fineract_to_account_id`, the latter indexed with `user_id` for the beneficiary guard.
* `fineract_standing_instruction_id`, unique, null until the row is linked: by confirm, or by a cancel that matched its instruction by name.
* `claimed_until`, set while a confirm is working on the unlinked row and cleared when it is linked or the outcome is unknown. A claim left by a confirm that died lapses after five minutes. The beneficiary guard treats a claimed row as a transfer being set up.
* `created_at` and `updated_at`.

The schedule itself (amount, frequency, dates) is not copied into the BFF: Fineract is the system of record and holds it on the instruction. The query side maps the same table read-only as `scheduledtransfers.query.domain.ScheduledTransferQueryEntity`.

== Audit

`SCHEDULED_TRANSFER_CREATED` (severity `INFO`, not client submittable) is published when a row is linked, with the scheduled transfer's `publicId` in its details. `SCHEDULED_TRANSFER_CANCELLED` (severity `INFO`, not client submittable) is published by each successful cancel confirm, with the same detail. The OTP challenge and any ABAC denial are audited by the shared OTP and ABAC code, as for every other step-up flow.

== Design rationale

Fineract already runs standing instructions on its own schedule, with run history and failure handling, so the BFF uses them instead of running a scheduler. A BFF scheduler would have to survive restarts, avoid double runs across instances, and reconcile with Fineract after partial failures; Fineract does all of that in one place.

The row is reserved before the Fineract call, rather than written after it, so a create can never leave an instruction the BFF does not know about. If the call's outcome is unknown, the reservation plus the forwarded idempotency key let a retry link the instruction Fineract created instead of creating a second one. The row holds only references; the schedule stays in Fineract, so the two cannot disagree.

Weekly and monthly every period cover the common recurring payments (rent, savings, allowances) without exposing Fineract's full recurrence options, each of which would need its own validation and UI.

The run history is bounded by a date window rather than by "the account's most recent N runs". Fineract cannot filter run history by instruction, so a count limit could be filled by a busy sibling instruction on the same account and push this transfer's own runs out. A date window cannot, because every run of the transfer inside it is read whatever else shares the account.

[[scheduled-transfers-limitations]]
== Limitations and future work

* *Active transfers only.* The list leaves out cancelled, disabled, and ended transfers. Their run history stays readable by `publicId`.
* *Run history is read by window.* Fineract cannot filter run history by instruction, so each request reads the source account's runs inside the window, including runs of other instructions on it, and pages in the BFF. The default window is the last twelve months, so older runs are not returned unless the client asks for an earlier window with `fromDate` and `toDate`, and `totalElements` and `totalPages` describe the window only. A window that holds very many runs of other instructions still costs a read of all of them.
* *A transfer being set up blocks changes to its beneficiary.* While a confirm holds its row, deleting the beneficiary or lowering its limit answers HTTP 409, even if that confirm then fails. The claim lasts until the confirm finishes, or five minutes if it died.
* *An unknown outcome nobody retries leaves an unlinked row.* If confirm fails with HTTP 425 or 502 and the customer never retries with the same key, the row stays unlinked even if Fineract created the instruction, which then runs. The list and run history still find it by the name its `publicId` determines (see <<scheduled-transfers-reads>>), but only a retried confirm or a cancel writes the link.
* *Savings to savings only.* No loan repayments, no one-off future-dated transfers, and no partial transfers.
* *The OTP channel is email.*
