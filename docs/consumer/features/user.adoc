= User Profile

The user module owns the logged-in customer's view of their own profile and the lifecycle of their BFF credentials (BFF: backend-for-frontend, the Spring Boot service that sits between the Angular client and Fineract Core). A "user" here is the BFF's own account record: an email, a password hash, and a binding to exactly one Fineract client. The module serves four read endpoints (profile, charges, obligees, profile image) and four write endpoints, all of which concern the password (authenticated change, and the public forgot/reset pair).

Code lives under `consumer/src/main/java/org/apache/fineract/consumer/user/`, split into `command/` and `query/` sub-trees per the project CQRS layout (CQRS: commands that mutate state and queries that read it are separated end to end, each side with its own controller, service, repository, and entity mapping).

There are no endpoints for updating profile fields. Name, email, mobile number, and the profile picture are maintained on the Fineract client record by back-office staff; the BFF only reads them.

== Query endpoints

Served by `UserQueryController` under the base path `/api/v1/user`, returning JSON. Every request must carry a valid access JWT (JSON Web Token, the signed token minted at login), which the security filter chain reads from the `access_token` httpOnly cookie. Each service method passes through the ABAC policy check (ABAC: attribute-based access control, authorization decided from attributes of the caller, the resource, and the request) before any Fineract call.

[cols="1,3,4,4", options="header"]
|===
| Method | Path | Purpose | Authorization

| GET
| `/api/v1/user/profile`
| The caller's own profile: `displayName`, `accountNo`, `active`, `memberSince` (the Fineract activation date), `maskedEmail`, `maskedMobile`, `kycVerified`, `hasImage`.
| Action `USER_PROFILE_VIEW`. Scope `consumer:full`. KYC not required.

| GET
| `/api/v1/user/charges`
| Client-level charges (fees Fineract has attached to the client record, distinct from account charges). Query parameters: `status` (`all`, `active`, or `inactive`; default `all`; anything else is rejected with HTTP 400, code `error.msg.consumer.user.charge.status.invalid`), `page` (default `0`), `size` (default `20`). Page numbers are translated to Fineract offset/limit as `offset = page * size`. Returns the mapped items plus `totalFilteredRecords`.
| Action `USER_CHARGES_LIST`. Scope `consumer:full`. KYC required.

| GET
| `/api/v1/user/image`
| The caller's profile picture as a base64 data URI (a `data:image/...;base64,...` string embeddable directly in an `<img>` tag). Optional `maxWidth` and `maxHeight` query parameters request server-side resizing. HTTP 404 with code `error.msg.consumer.user.image.not.found` when no image exists.
| Action `USER_IMAGE_VIEW`. Scope `consumer:full`. KYC not required.

| GET
| `/api/v1/user/obligees`
| Guarantor obligations: loans on which the caller stands as guarantor (display name, account number, loan amount, guarantee amount, amounts released and transferred).
| Action `USER_OBLIGEES_VIEW`. Scope `consumer:full`. KYC required.
|===

Upstream Fineract failures on any of these reads are translated to HTTP 502 with code `error.msg.consumer.user.upstream.unavailable`; Fineract error details are not leaked to the client.

== Command endpoints

Served by `UserCommandController` under the same base path. All four require the `X-Device-Fingerprint` header (a client-generated device identifier). On the authenticated change endpoints the requirement is enforced by `DeviceFingerprintFilter`, which rejects any authenticated request without the header. The public forgot and reset endpoints carry no JWT, so the filter passes them through; on those two the header is required only by the controller's `@RequestHeader` binding. New passwords must satisfy `PasswordPolicy`: 15 to 64 characters with at least one lowercase letter, one uppercase letter, one digit, and one symbol, validated by Bean Validation on the request DTO.

[cols="1,3,4,4", options="header"]
|===
| Method | Path | Purpose | Authorization

| POST
| `/api/v1/user/password/change/initiate`
| Start a logged-in password change. Body: `currentPassword`. Verifies the current password (HTTP 403, code `error.msg.consumer.user.password.invalid` on mismatch), sends a one-time code (OTP) to the user's email, and issues a step-up token (a short-lived proof of re-authentication) bound to the caller, their device fingerprint, and this specific action, valid 5 minutes. Returns `stepUpToken`, `expiresAt`, and the masked destination email.
| Authenticated session. Action `USER_PASSWORD_CHANGE`. Scope `consumer:full`. KYC not required.

| POST
| `/api/v1/user/password/change/confirm`
| Complete the change. Body: `stepUpToken`, `otp`, `newPassword`. Verifies the step-up token against the caller, device fingerprint, and action (HTTP 401, code `error.msg.consumer.user.stepup.invalid` on failure), validates the OTP, stores the new hash, revokes every existing session, and reissues fresh access and refresh cookies so the current device stays logged in.
| Authenticated session. Action `USER_PASSWORD_CHANGE`. Scope `consumer:full`. KYC not required.

| POST
| `/api/v1/user/password/forgot`
| Request a reset code while logged out. Body: `email`. Always returns HTTP 202; if the email matches a user, an OTP is emailed asynchronously. The response is identical for known and unknown emails, so the endpoint cannot be used to probe which addresses are registered.
| Public (`permitAll` in `SecurityConfig`).

| POST
| `/api/v1/user/password/reset`
| Complete the reset. Body: `email`, `otp`, `newPassword`. Stores the new hash and revokes all sessions. Unknown email and invalid OTP both return the same HTTP 400, code `error.msg.consumer.user.password.reset.invalid`, again to prevent enumeration.
| Public (`permitAll` in `SecurityConfig`).
|===

The initiate and forgot paths publish a `PASSWORD_CHANGE_INITIATED` audit event; the confirm and reset paths publish `PASSWORD_CHANGE_CONFIRMED`. Each event carries a `flow` detail of `change` or `reset`. Session revocation is delegated to the authentication module (`AuthenticationCommandService`), which owns refresh-token state.

== Internal service surface

Beyond its HTTP endpoints, the module exposes service methods that other modules call through the Spring Modulith named interfaces:

* `UserCommandService.create(...)` and `markOtpVerified(...)` are called by the registration module to persist a new user in `PENDING_OTP` status and flip it to `BOUND` once the registration OTP verifies. They are not reachable over HTTP.
* `UserQueryService.findByPublicId(...)` is a read lookup used by the registration, loans, transfers, and beneficiaries modules to resolve a user's public UUID to the bound Fineract client id; `findById(...)` and `findCredentialsByEmail(...)` are exposed on the same interface.
* `PrincipalUserLookupAdapter` and `PrincipalUserAuthLookupAdapter` implement lookup ports declared by the access infrastructure and the authentication module, so those consumers depend on a port, not on this module's repository.

== Profile picture handling

The read path is a proxy. `UserQueryServiceImpl.getImage` resolves the caller's Fineract client id and calls Fineract `GET /v1/clients/{clientId}/images` through the generated client (`DefaultApi.retrieveImage`) with entity type `clients` and an `Accept: text/plain` header. Under that accept header, upstream Fineract (`ImagesApiResource`) base64-encodes the stored image and wraps it as a data URL; when both `maxWidth` and `maxHeight` are supplied it resizes first. The BFF returns the string unchanged inside `UserImageQueryData.imageDataUri`. A Fineract 404 is translated to the BFF's own 404; any other Feign failure becomes a 502.

Writes are deliberately excluded. Fineract exposes create and delete operations on the same image resource, but the BFF offers no upload, replace, or delete endpoint. The photo is captured by back-office staff and serves as an identity-verification anchor: staff compare the person in front of them (or on a document) against the stored image. Letting the consumer overwrite it from a self-service channel would let a compromised session replace the very artifact used to detect that compromise. The profile response carries `hasImage` (from Fineract's `imagePresent` flag) so the client can decide whether to fetch the image at all. This is a deliberate deviation from the deprecated self-service API, which allowed image upload.

== Data sources: Fineract versus BFF-local

The BFF stores no copy of profile data. Every profile, charges, obligees, and image read fetches live from Fineract via the generated Feign client (`ClientApi`, `ClientChargesApi`, `DefaultApi`); nothing from those responses is persisted locally.

[cols="2,3", options="header"]
|===
| Source | Fields

| Fineract client record, fetched per request
| Display name, account number, active flag, activation date, email address, mobile number, image-present flag, the image itself, client charges, obligee details.

| BFF `users` table
| Login email, password hash, public UUID, bound Fineract client id, binding status, binding timestamp, created/updated timestamps.

| JWT claim
| `kycVerified` in the profile response is read from the access token's `kyc_verified` claim, which the token-mint pipeline populated from a live Fineract standing check. The profile endpoint does not re-check Fineract for it.
|===

== Security

* Contact details are masked before they leave the BFF. `EmailMaskingService` masks the email; the mobile number is reduced to `+***-***-+` plus the last four digits. The raw email and mobile number are never returned by any endpoint in this module.
* The password hash never crosses the HTTP boundary. It travels internally in `UserCredentialsQueryData`, whose `toString` is explicit-include-only so it cannot leak into logs; the same applies to every request DTO that carries a password or OTP.
* Password change is a step-up flow with three factors: knowledge of the current password, possession of the email inbox (OTP), and a step-up token cryptographically bound to the caller's public id, device fingerprint, and the action fingerprint of `/api/v1/user/password/change`. A step-up token minted for one device or one action cannot confirm another.
* Both password-setting flows revoke all sessions, so a session an attacker holds dies the moment the legitimate user changes the password.
* The forgot and reset endpoints are shaped against user enumeration: uniform 202 on forgot, one generic error code on reset, and log lines that record the failure without the submitted email.
* KYC gating is differential: `USER_CHARGES_LIST` and `USER_OBLIGEES_VIEW` require the `kyc_verified` claim, while `USER_PROFILE_VIEW`, `USER_IMAGE_VIEW`, and `USER_PASSWORD_CHANGE` do not, so a customer whose Fineract client is not in good standing can still see who they are and recover their credentials, but cannot read financial data.

== Data model

The module owns one table, created by the Liquibase changeset `consumer/src/main/resources/db/changelog/user/001-create-users-table.yaml` (Liquibase: the versioned database-migration tool; all schema changes in this project go through it).

`users`:

[cols="2,2,4", options="header"]
|===
| Column | Type | Notes

| `id` | BIGINT identity | Internal primary key, never exposed externally.
| `public_id` | UUID, unique | External identifier; the JWT subject.
| `email` | VARCHAR(255), unique | Login identifier.
| `password_hash` | VARCHAR(100) | Encoded by Spring Security's delegating `PasswordEncoder`.
| `client_id` | BIGINT, unique | The bound Fineract client id. One user per client.
| `status` | `user_status` PostgreSQL enum | `PENDING_OTP` or `BOUND`.
| `bound_at` | TIMESTAMPTZ | Set when registration OTP verification completes.
| `created_at`, `updated_at` | TIMESTAMPTZ | Maintained in entity code, not by triggers.
|===

Two JPA entities map this table, one per CQRS side: the mutable command entity `User` (construction only through the `createPendingOtp` factory; `markOtpVerified` performs the binding transition and raises HTTP 409, code `error.msg.consumer.user.binding.state.invalid`, when the user is not in `PENDING_OTP` status; `changePassword` replaces the hash without a state guard) and the read-only `UserQueryEntity` (Hibernate `@Immutable`). `UserQueryRepository` projects directly into DTOs via JPQL constructor expressions, so query callers never receive an entity.

== Testing coverage

* Unit tests: `UserCommandServiceImplTest` covers user creation including the unique-constraint race, OTP-verified transition, both password-change steps with wrong-password, invalid step-up, invalid OTP, and policy-denial paths, and the forgot/reset pair including the unknown-email branches. `UserQueryServiceImplTest` covers the internal lookups, profile mapping and masking including null contact fields, charges paging and status validation and KYC denial, obligees, and image retrieval including the 404 translation, scope denial, and upstream failure.
* Cucumber end-to-end: `profile.feature` (5 scenarios) exercises profile, charges, and obligees against a seeded customer, the image not-found path, and rejection of all four query endpoints without a session. `password.feature` (6 scenarios) exercises the full change flow with real OTP retrieval from Mailpit, session reissue and old-token rejection, wrong current password, the full reset flow, enumeration-safe forgot for unknown emails, and wrong-OTP rejection.

== Design rationale

* No local mirror of profile data. Fineract is the single source of truth for client details; the BFF proxies reads per request instead of synchronizing a copy, which removes an entire class of staleness and reconciliation problems at the cost of one upstream call per read.
* Profile picture is read-only by design. The image anchors back-office identity verification, so the consumer channel must not be able to replace it (see Profile picture handling above).
* Contact details are masked because the profile page has no need for the full values, and returning them would turn any XSS or logging slip into a PII leak.
* The credential row lives in this module while session state lives in the authentication module. Password confirmation crosses that boundary through the `AuthenticationCommandService` interface rather than touching token storage directly, keeping each module's persistence private.
* Public forgot/reset endpoints return uniform responses so the login identifier space cannot be enumerated, matching the behavior of the login endpoint itself.
* The differential KYC gate treats identity ("who am I, can I fix my password") as available to any bound user, and financial detail as gated, mirroring the ABAC policy split used across the read modules.

== Limitations and future work

* *The fingerprint header is unused on reset paths.* The `X-Device-Fingerprint` header is required on the public forgot and reset endpoints but is not bound into the reset flow or its audit events (they record a null fingerprint), so it adds no security value on those two paths.
* *Charges pagination lacks page metadata.* The response returns `totalFilteredRecords` but not current page or total pages; clients must derive it.
