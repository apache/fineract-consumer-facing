= PII and Secrets on the Client

The client's data-hygiene rule is simple: nothing secret and nothing personally identifying (PII: data that identifies a person, such as an email address or a government ID number) may persist in the browser or leave it through a side channel. This section covers what browser storage actually contains, how sensitive inputs are rendered, how the audit pipeline scrubs events before they leave the page, and how errors are displayed. The server half (encryption at rest, masked responses, and the BFF's own PII screen) is described in `docs/consumer/security/secrets.adoc` and, for the audit gate, `docs/consumer/features/audit.adoc`.

== What lives in browser storage

Grepping the application source for `localStorage` yields exactly two keys, and sessionStorage is not used at all:

[cols="1,2,3", options="header"]
|===
|Key |Written by |Contents

|`bff.device-id`
|`core/auth/device-fingerprint.ts`
|The random device UUID, an identifier rather than a secret (see xref:device-fingerprint[Device Fingerprint])

|`app.lang`
|`core/i18n/i18n.service.ts`
|The chosen language code (for example `en`)
|===

No token, credential, account number, or user attribute is ever written to storage. The access and refresh tokens are httpOnly cookies (cookies page JavaScript cannot read) managed entirely by the BFF; the session signal holds only an expiry timestamp; step-up challenges live in in-memory signals that vanish on reload (see xref:session[Session Model] and xref:step-up[Step-Up Challenges]).

== Sensitive inputs

Fields whose value is a secret are rendered as `type="password"` so the value is masked on screen, kept out of shoulder-surfing range, and excluded from ordinary browser autofill history. These fields are the login and registration passwords, both password-change fields, the password-reset field, and, notably, the registration `documentKey`, which is the raw SSN or Aadhaar number (`features/registration/registration.component.ts`, with `autocomplete="off"`). After submission the BFF returns only `maskedLastFour`; the full number never comes back to the client. The OTP field (`shared/otp/otp.component.ts`) is visible while typed, since codes are short-lived and single-use, but it uses `autocomplete="one-time-code"` and is never stored or logged.

== Audit events are scrubbed before they leave the browser

The client audit pipeline (`core/audit/audit.service.ts`) batches navigation, sensitive-action, and error events to `POST /api/v1/audit/events`. Every `details` map passes through `buildDetails` in `core/audit/pii-scrub.ts` before it is buffered:

* *Blocked keys.* Entries whose key is `password`, `otp`, `ssn`, or `token` (case-insensitive) are dropped entirely, whatever their value.
* *Pattern redaction.* `scrubPii` replaces anything shaped like an email address, a 9-digit run (SSN-like), a 12-digit run (Aadhaar-like), or a 13-to-19-digit run (card-number-like) with `[REDACTED]`.
* *Length cap.* Each value is truncated to 300 characters, bounding how much of any unexpected payload can ride along.

The two automatic producers stay coarse by construction. `errorInterceptor` records failed calls as an endpoint template with numeric and UUID path segments replaced by `:id` (never query strings or bodies). `AuditErrorHandler` (`core/audit/audit-error-handler.ts`) records only an exception's message and top stack frame, both passed through `buildDetails`.

The client scrub is a courtesy, not the gate. The BFF re-screens every submitted event server side (`AuditPiiScreen`) against the same email, SSN-like, Aadhaar-like, and card-like patterns and the same forbidden keys, and drops any event that matches. A tampered client therefore cannot smuggle PII into the audit table. See `docs/consumer/features/audit.adoc`.

== Errors never display raw payloads

`errorInterceptor` turns every failure into a toast whose text is resolved in strict order. It first tries the BFF's machine-readable `code` translated through the i18n catalog, then the BFF's `defaultMessage` (a safe, human-written sentence composed server side), then a generic translated fallback. Raw response bodies, stack traces, and HTTP status pages are never rendered, so an upstream error cannot leak internals or reflected input into the UI.

== Test coverage

The Playwright end-to-end spec `frontend/playwright/tests/registration.spec.ts` walks the full registration flow with a known OTP code and a known document key. It then dumps both `localStorage` and `sessionStorage` and asserts that neither value appears anywhere in them. This is a regression trap on the "secrets never persist" rule at the point where the client handles its most sensitive input.
